# TalentLens

[![CI](https://github.com/ratatall/talentlens/actions/workflows/ci.yml/badge.svg)](https://github.com/ratatall/talentlens/actions/workflows/ci.yml)

A recruiting search portfolio project built with **Next.js 16, React 19, TypeScript, Node.js route handlers, and OpenSearch**. Candidate explanations are exact source excerpts, and relevance feedback proposes explicit skill priorities for the user to accept.

## Run immediately

Requires Node.js 20.9+ (Node 22 LTS recommended).

```sh
npm ci
npm run dev -- --hostname 127.0.0.1
```

Open http://127.0.0.1:3000. No API key is required for the clearly labeled demo mode. It searches 360 deterministic synthetic profiles using local keyword overlap. It does **not** simulate semantic search or claim to use an LLM.

## Enable real OpenSearch

Docker must be running. The Compose service disables authentication **only for local development** and binds to loopback.

```sh
docker compose up -d --wait
cp .env.example .env.local
npm run seed
```

Set `SEARCH_BACKEND=opensearch` in `.env.local`, then restart the app. Keyword queries now use OpenSearch BM25 with skill and experience filters. The seed step creates a new index and intentionally refuses to overwrite an existing index. If an initial seed fails or a schema changes, choose a fresh `OPENSEARCH_INDEX` value and seed again. A partial index may contain a subset of the profiles; the seed command must finish successfully before use.

## Enable LLM interpretation and hybrid search

Add your own `OPENAI_API_KEY` to `.env.local`. This stays on the Node.js server. The Responses API extracts reviewable criteria; the embeddings API creates 512-dimensional vectors with `text-embedding-3-small`. Model names are configurable.

For an existing keyword-only index, choose a **new index name** such as `talentlens-profiles-v2` and run:

```sh
npm run seed -- --embeddings
```

This makes paid provider requests to embed all synthetic résumés. Restart the app. The Hybrid control retrieves BM25 and vector candidates from OpenSearch and combines their ranked lists with application-side reciprocal rank fusion (RRF, k=60). Both retrieval paths apply the same hard filters. Hybrid retrieves up to 100 candidates per branch and returns at most 50 results; the displayed total is the size of that retrieved union, not an exhaustive corpus count or a relevance probability.

The index records embedding model metadata. An index missing compatible embeddings produces an actionable error instead of silently falling back. Provider failures also stay visible. LLM-generated criteria are validated and reviewed before application. Explanations are never generated by the model.

## Product flow

1. Describe the role and choose **Interpret brief**.
2. Review extracted requirements, then **Apply & search**.
3. Add/remove required skills, edit minimum years or search method, then **Update results**.
4. Inspect profile excerpts and missing evidence.
5. Mark profiles relevant, then explicitly accept suggested priorities.
6. Save profiles to the device-local shortlist. “Not relevant” hides a profile for the active workspace session; Restore hidden reverses it.

Shortlist data is stored only in this browser. Feedback and priorities are session state. No shared accounts, uploaded personal data, or hiring decisions are implemented.

## Architecture

```text
React workspace → Next.js Node.js API routes
                     ├─ /api/interpret → rule parser OR LLM structured output
                     └─ /api/search → local keyword demo OR OpenSearch
                                         ├─ BM25 retrieval
                                         ├─ vector k-NN retrieval (hybrid)
                                         └─ reciprocal rank fusion
                          → exact profile excerpts → results + feedback
```

- `src/lib/profiles.ts`: deterministic fictional dataset, 12 specialties × 30 variations.
- `src/lib/ranking.ts`: demo ranking, hard filters, exact evidence, RRF.
- `src/lib/opensearch.ts`: real search adapter, HTTP connection and optional basic authentication.
- `src/lib/provider.ts`: server-only LLM interpretation and embeddings integration.
- `scripts/seed.ts`: non-destructive index creation and optional batch embeddings.
- `scripts/evaluate.ts`: repeatable 30-query synthetic sanity benchmark.
- `tests/`: retrieval invariants and integration contracts.

## Validate and evaluate

```sh
npm test
# Also exercise a running, seeded OpenSearch service:
RUN_OPENSEARCH_TESTS=1 npm test
npm run lint
npm run typecheck
npm run build
npm run evaluate
# With a seeded embedding index and provider key:
npm run evaluate -- --hybrid
```

Evaluation reports are saved in `data/evaluation-<backend>-<mode>.json`, with precision@5, response latency, embedding-token usage, and ranked IDs. **These labels are skill-based synthetic sanity checks, not independent recruiter judgments.** Ten held-out paraphrases share topics with development queries. Do not report these scores as real-world hiring quality or claim a hybrid improvement without running both modes on an independently judged dataset. Provider dollar cost is not estimated; token usage is recorded for reconciliation with actual billing.

## CI and independent evaluation

GitHub Actions runs lint, type checks, unit/contract tests, and a production build on every push and pull request. A separate job starts OpenSearch, seeds the corpus, exercises real BM25 and filtered vector retrieval with fixed test vectors, and uploads the synthetic sanity benchmark. CI does not use paid API keys.

The [paired evaluation protocol](docs/EVALUATION.md) adds frozen query briefs, blinded human judgment packets, precision@5, pooled nDCG@5, latency percentiles, and explicit token-cost estimates. **Paid collection and independent human relevance judgments are still pending; no semantic quality improvement is claimed.**

## Current boundaries

- The rule parser recognizes explicit skill names and years only; complex negation, role constraints, location, and nuanced intent need review. Unknown constraints are not silently converted to hard filters.
- Name and location are displayed but excluded from demo ranking and retrieval text. Evidence reflects the fictional source, not verified ability.
- The app is a local portfolio MVP, not an authenticated multi-tenant service. Before public deployment, add authentication, per-user storage, rate limiting and cost controls, and secure the OpenSearch network. Current API validation, body limits, same-origin browser checks, and timeouts do not replace authentication.
- No AWS SQS or Spark is included yet. A queue becomes useful when adding background ingestion at larger scale; this project currently indexes 360 profiles in a bounded script.
